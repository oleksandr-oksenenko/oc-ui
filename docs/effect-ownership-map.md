# Effect ownership map and launcher evidence

Updated against the migration implementation in this worktree, using OpenCode `0.0.0-beta-18866`, Effect `4.0.0-rc.112` and matching atom-solid. Combined checks and packaged runtime acceptance passed on 2026-09-05. Launcher findings originally came from main `f9554f8`.

The [application architecture](./effect-architecture.md) defines ownership and failure policies. This map records their implementation locations and the launcher evidence.

The earlier phrase “SDK compatibility boundary” means the existing SDK data store inside Workspace. The upstream helpers and Solid store run inside Workspace and remain authoritative for SDK-managed data and behavior. Reimplementing its cache, optimistic updates, rollback and event handling is outside this migration. Revisit this boundary only if OpenCode ships suitable Effect-based helpers and stores, then verify behavior parity before adopting them.

Feature Effects replace manual Promise/liveness coordination for sessions, recovery, composer admission, selections, forms, changes and session/project operations. Atoms hold oc-ui-owned state and drafts. SDK data accessors remain the source for cached server records. Existing draft snapshot and explicit retry matching protect local edits; they do not replace SDK acknowledgement or rollback. No new automatic mutation retry policy is introduced.

## Preserved launcher behavior

1. **The process is app-owned and lazy.** Main forks an Electron utility process on demand. It sends a fresh password and user-data path after spawn. There is no detached CLI daemon to discover or adopt. A saved local choice only preselects the form; startup still requires an explicit action.
2. **Listening is earlier than readiness.** The worker prepares the environment before importing the server, creates a scope, and invokes upstream `ServerProcess.start`. Its `onListen` callback reports the loopback address before application boot completes. Main then checks authenticated health, the exact version and this child's PID. The listener message alone is insufficient. The callback receives a shutdown signal; the shutdown effect returned by `start` only waits. The worker must close its retained scope to release resources.
3. **Main owns failed boot and termination.** Upstream can expose failed health without rejecting the worker's startup Promise. Main retains its startup deadline and health checks. Startup failure waits for child cleanup before rejecting. Stop requests allow 10 seconds for graceful exit, then two 2-second escalation waits. A missed deadline never releases the child record: only Electron's exit notification does.
4. **Quit has a retryable preparation step.** Main confirms Quit and stops the child before disposing main services. Cancel preserves the running child. If stopping fails, retain the service for another Quit attempt. Current code closes admission to new local connects once shutdown starts, even if that stop fails. A runtime finalizer alone cannot express this behavior.
5. **Configuration and storage have different roots.** The worker redirects config to `<userData>/opencode/config`, clears inherited config overrides and enables project config discovery. It explicitly chooses a persistent database because the library default is memory. The default database remains under OpenCode's data root; `OPENCODE_DB` can override it. Changing Electron user data does not isolate that database or all upstream configuration sources.
6. **Three credentials have different owners.** Main generates the temporary local HTTP password; Settings may encrypt a saved remote password; upstream OpenCode stores provider credentials in its database. None should be merged into a new desktop credential abstraction.
7. **Packaging is part of the launch boundary.** Development and packaging build the worker for Node with the pinned OpenCode library bundled, external packages staged with their dependency versions, and native/WASM assets retained. Current staging supports macOS arm64. Moving work into services must preserve this separate worker entrypoint and its runtime package assets.

Closing the last window on macOS can leave main and the worker alive; reopening creates a fresh renderer. Work already accepted by OpenCode belongs to the server and can continue without that renderer. Renderer-owned pending work cannot survive destruction of its JavaScript process; stronger guarantees would require a separate, explicitly designed main/server contract.

## Evidence and checks

The original launch investigation checked graph generation `2026-09-04T10:30:39Z`, with no recorded gaps in the relevant indexed source. That historical generation is not evidence for this migration. Graph transport was unavailable during the current update, so the files linked above and installed SDK source were read directly. This is bounded source evidence, not an exhaustive audit.

The pinned [SDK data implementation](../apps/desktop/node_modules/@opencode-ai/client/dist/solid/data.js) owns optimistic admission, ordered sends, acknowledgement, rollback and event reconciliation. The [SDK connection helper](../apps/desktop/node_modules/@opencode-ai/client/dist/solid/connection.js) owns its stream and transport retries. Both retain their Solid lifecycle hooks.

[Worker build configuration](../apps/desktop/electron.vite.config.ts), [dependency staging](../tools/stage-opencode.mjs) and the [packaged acceptance scenario](../apps/desktop/test/e2e/packaged-startup.e2e.ts) remain the evidence locations for bundling and real-process behavior, including lazy launch, reload/reuse, crash restart, Quit and PTY cleanup.

Current migration verification passed:

- `pnpm check`: formatting, typed Effect lint, TypeScript, styles, component layout and unused-code checks.
- `pnpm test`: 82 files and 638 tests, including browser Storybook interactions and focused ordering, interruption, settlement and remount regressions.
- `pnpm test:acceptance:mac`: rebuilt and verified the signed macOS arm64 package; exercised authenticated startup, reload/reuse, crash/restart, Cancel/Quit and PTY cleanup. The same real Electron run covered directory navigation, empty/loading states, dialog Escape/reopen/focus, narrow scrolling, two session creations and draft restoration. Final narrow and desktop screenshots were inspected.

Independent main and renderer reviews have no remaining actionable findings. The migration adds no automatic retries and retains the pinned SDK helpers and store. Packaged verification uses an isolated profile and sends no model prompts; provider execution is covered by existing SDK boundaries and focused application tests, not a live provider call.
